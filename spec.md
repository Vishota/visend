# visend specs

## TLDR

Цель - быстрое к установке и настройке в разных средах приложение, позволяющее отправлять себе в telegram файлы и сообщения

Ключевые моменты:
- получение данных через stdin - pipe `|`
- режимы - файл и текст
- безопасное хранение токена при работе без сервера-посредника (`~/.config/visend/` + `chmod 600`; на Windows - файл в профиле юзера, права ограничиваем ACL)
- мой общий бот, работающий через сервер-прокси. Юзер в таком случае указывает только свой user id. Бот при любом сообщении от юзера даёт ему его user id
- ценность - быстрая установка и настройка в любой среде (win/linux; npx/pacman/apt/apk/winget(?)/etc; зальётся на основные зеркала популярных дистрибутивов)
- без зависимостей для устанавливаемого cli - работает на простом curl/че там у винды/для ноды модули `http`/`https`. Зависимостей, в т.ч. dev - 0. Наиболее совместимый синтаксис из возможного - на nodejs старой версии из-за отсутствия fetch api ничего не должно сломаться. Минимальная версия node - 10, тестируем на 10, 12, 16, 24 (`engines` в package.json)
- юзера предупреждаем, что бот для dev и pet проектов, не для чувствительной информации, особенно - через мой сервак (при выборе моего сервера показываем отдельно warning)

## Команды CLI

Сам пакет зовется `visend`  
Если через pipe идет инфа, например, просто `ls | visend`, то по умолчанию предполагаем команду `text`. Если нечего слать (например, вызвали просто `visend` без stdin), то предполагаем `help`.  
Если `visend file` / `visend text` вызваны без stdin и без аргументов - ошибка с hint, а не help.

### setup

1. Спрашиваем свой бот или сервер  
   - Через сервер (если сервер недоступен - неактивно с инфой о том, что установленный сервер не отвечает, подробнее - `visend server`)
     - Предупреждаем о рисках (просто вывод). Пишем, что при желании можно поднять свой сервер из докер образа, подробнее - `visend server`
     - Даём ссылку на бота и пишем, что надо ему написать для получения кода (защита от спама через сервер) и user_id
     - По отправке `/start` боту сервер шлёт юзеру одноразовый код  
     - Запрашиваем user id и код
   - Через своего бота
      - Запрашиваем токен бота
      - Проверяем через getMe валидность токена + получаем тег бота
      - Пишем, что надо написать `/start` боту - и ждём его через getUpdates (см. «Детали по поллингу»). Обнаружив `/start`, показываем в терминале user_id и @username (если есть) - Enter сохраняет, иначе ручной ввод. Ручной ввод user_id остаётся fallback'ом (подсказка: id можно узнать у @userinfobot)
2. Шлем через бота юзеру, что все настроено

### file [path] [--name <string>] 

Отправляем файл.  

Если есть stdin - шлём его как файл (указанный name либо `visend.txt`). Stdin буферизуем во временный файл, так размер известен до отправки.  
Если есть аргумент path - шлём его (указанный name либо оригинальное имя файла; --name без расширения оставляем как есть). Размер проверяем по stat заранее.  
Если есть stdin и path, то предпочитаем path и выводим warning о том, что stdin ignored  
Локально проверяем размер - >50Mb - пишем, что в телеге лимит 50 мегабайт. Также при отправке через сервер там может стоять свой лимит - если уперлись в него, то пишем, что лимит серверный  

### text [text] [--force-as-text]

Отправляем текст.  

Перепроверяем что мы не пытаемся перевести бинарные данные в текст. Если детектим это, то выводим предупреждение, показываем юзеру маленький кусок того, что он собирается отправить (кашу, скорее всего), переспрашиваем, точно ли оно ему надо Y/N. Если да - идем дальше (по остальным проверкам и затем шлём). Если нет - прерываем с подсказкой использовать `visend file`  
Если по pipe идет инфа - шлём её.  
Если есть аргумент text - шлём его.  
Если есть stdin и text, то предпочитаем text и выводим warning о том, что stdin ignored  
Если длина текста >4096, то отправляем как `visend.txt` и выводим варнинг о том, что лимит длины сообщения в Telegram 4096 символов. Предлагаем флаг `--force-as-text` чтобы слать текстом несмотря на то, что его порежет  
Несколько аргументов через пробел в духе `visend text hello world` склеиваем в одно сообщение    
Бинарный детект срабатывает раньше лимита длины (бинарные данные >4096 - сначала переспрос про бинарность)

### forget [-y|--yes]

Забываем все настройки (кроме сервера!), удаляем токен. Предварительно просим подтверждения

### server

Выводим текущий url сервера  
Выводим его статус и ссылку на бота, через которого он шлет инфу  
Если недоступен, то так и пишем и сообщаем о возможности поднять свой    
URL по умолчанию - visend.vishota.com  

#### server set <url>

Проверяем доступность.  
Если недоступен, то выводим warning, спрашиваем, хочет ли юзер все равно сохранить этот url.  
В том числе позволяем указывать порт и путь (i.e. `http://example.com:6767/test/misc/visend`)  
Если URL начинается с http:// - предупреждаем, что токен и данные пойдут по сети без шифрования; спрашиваем, продолжать ли (Y/N)  
Если выбран режим работы через сервер - показываем сообщение о том, что в целях безопасности после смены сервера надо снова сделать `visend setup` и ввести одноразовый код (новый сервер не примет токен), и что старый токен удалён автоматически. В режиме своего бота это сообщение не показываем - токен бота от сервера не зависит

#### server reset [-y|--yes]

Устанавливаем (после подтверждения) сервер `visend.vishota.com`. Судьба токена и сообщение про re-setup - как в `server set`

### settings

Выводим настройки

### help

Помощь

## Правила для разработки

### Детали по поведению

Статус отправки логируем - не молчим. Максимальную инфу даем о том, что за ошибка в случае ошибки.  
Инфу о ссылке на бота получаем с установленного в данный момент сервера - никакого хардкода (в целом ни к чему не привязываемся; всё, что стоит по умолчанию - сервер visend.vishota.com). Её не храним, а получаем каждый раз при необходимости  
Если не установлен способ отправки - пишем юзеру типа напишите `visend setup` сначала  
В командах - флаги после позиционных аргументов  
Подтверждения (Y/N) читаем не из stdin, а с /dev/tty (Windows - из консоли): stdin занят данными пайпа. Без TTY и без -y - прерываем с ошибкой  
CLI и бот работают только на английском.  
README.md - на английском + README.RU.md на русском  
-y/--yes = «отвечать да на все промпты»  

### Детали по поллингу (setup, режим своего бота)

- Первый вызов getUpdates - только чтобы узнать последний update_id; его результат юзеру не показываем (старьё в очереди)  
- Дальше поллиним с offset = update_id + 1 (long polling, timeout=25); каждый ответ ack'аем - апдейты не обрабатываются повторно  
- Пока ждём - выводим "Waiting for your /start..."  
- Получив /start: показываем user_id и @username (если есть); Enter - сохранить, иначе ручной ввод  
- Лимит ожидания - 120 секунд; по истечении - ошибка + fallback на ручной ввод user_id  
- 409 от getUpdates = на боте активен webhook (или второй поллер): объясняем, предлагаем deleteWebhook с подтверждением Y/N (сломает существующую интеграцию бота); при отказе - ручной ввод id

### Сервер

Нужен в качестве:
- глобальной точки входа для юзеров, которые хотят очень быстро что-то себе скинуть / не создавать бота вообще  
- способа не хранить токен telegram на устройстве  
- подъем своего сервера - способ полностью контролировать путь своих данных; также возможно, что центральный сервер хостить я уже не буду, в таком случае юзабельность сохранится за счет возможности работать на своём сервере

Эндпоинты:
- GET status
- GET config (выводит как конфиг - на данный момент максимальный размер файла и ссылку на бота)
- POST connect (body = JSON {"user_id": ..., "code": "..."} - в ответ токен)
- POST text (Authorization: Bearer <token>, body = raw UTF-8 текст)
- POST file (Authorization: Bearer <token>, body = raw bytes, имя файла в query (?name=..., URL-encoded))

Файл в raw body. multipart для совместимости с любой системой и версией не делаем. Токен - только в Authorization header, не в query (query пишется в access-логи прокси). Возвращаем результат отправки, его же отображаем в самой утилите после попытки отправки. Проверка только через токен.  

Токен - JWT (HS256, jose), внутри только user_id; сервер токены не хранит, проверяет подпись. Ревокации конкретного токена нет - «logout all» = смена SERVER_SECRET; это осознанный tradeoff для dev-тула  

Через docker secrets принимаем токен telegram бота и SERVER_SECRET (секрет для подписи JWT; рестарт с тем же секретом = токены живы, volume не нужен)  

Через env принимаем разрешенные user_id (на случай, если сервер захотелось поднять для себя)  

POST connect: не более 5 неверных попыток на user_id - код сгорает (юзер запросит новый через /start); per-IP rate limit 10 req/min  

Сам сервер также отвечает через бота:
- `/start` - выпускает код (8 символов [A-Z0-9], без похожих 0/O и 1/I), отправляет user_id и код, указывает время действия кода (пусть 1 час). При этом старый код перезаписывается  
- `/status` - показывает типа всё ок и аптайм шлёт

При старте сервера шлем через `setMyCommands` список команд  

Пишет пусть на английском

Сервер получает апдейты бота через getUpdates-поллинг, поэтому инстанс может быть только один (два поллера = 409). Коды храним в памяти (Map): TTL 1 час, один активный на юзера - персистентность не нужна, рестарт = юзер перепройдёт /start. Никакой внешней БД (Redis/PostgreSQL) не требуется; self-host - один контейнер без volume

Стек: TS+Node.js  
Базовый образ: FROM node:24-alpine3.24  
Зависимости: Express, jose

## Релизы

Версионирование - semver. Релиз = тег `vX.Y.Z`. Пуш тега запускает CI, который собирает и публикует всё сам.

Всё, что требует отдельного от исходников билда, собирается в `releases/<tag>/` - каждый релиз в своей папке. В git не коммитим (.gitignore) - артефакты живут в GitHub Release, на gh-pages и в registry:

    releases/v1.2.3/
    ├── visend-1.2.3.tar.gz     # исходники (git archive) - источник для AUR и apk-сборки
    ├── checksums.txt           # sha256 всего содержимого папки
    ├── deb/visend_1.2.3_all.deb
    ├── apk/visend-1.2.3-r0.apk
    └── winget/                 # фаза 2

### Каналы установки

- npm: `nodejs/` публикуется как пакет `visend` → `npx visend` / `npm i -g visend`. version в package.jsсинхронизируем с тегом
- apt (debian/ubuntu): свой статический репозиторий на gh-pages (`apt/`: pool + dists + подписанный InRelease). Пакет `all`, Depends: `nodejs (>= 16) | curl`
- apk (alpine): свой статический репозиторий на gh-pages (`apk/`: подписанный APKINDEX.tar.gz; кладём в x86_64 и aarch64 - пакет noarch). depends: `curl`
- pacman (arch): AUR-пакет `visend` - PKGBUILD качает tarball с GitHub Release, собирается у юзера. В официальные репы не лезем - долго и незачем, AUR достаточно
- winget: фаза 2. winget требует exe → бандлим nodejs-версию с рантаймом (node SEA или pkg - чисто CI-инструмент, не зависимость) → portable zip в GitHub Release → PR в microsoft/winget-pkgs. Бонус: exe работает без установленного node. Если захочется закрыть windows побыстрее - scoop-манифест на тот же zip делается за минуты
- docker: образ из `server/` → ghcr.io (`visend-server:<tag>` + `latest`), зеркало на Docker Hub - опционально

deb/apk/AUR ставят обе nix-платформы (nodejs/ + bash/) и dispatcher `/usr/bin/visend`: node >= 16 если есть, иначе bash+curl. powershell-версия живёт только в windows-каналах (winget/scoop) - в nix-пакетах не нужна.

Хост репозиториев - gh-pages: repo.visend.vishota.com через CNAME (fallback - <user>.github.io/visend). Публичные ключи и установочные команды для каждого канала - в README (ru/en).

### Шаблоны упаковки

Живут в `packaging/` в репо (это исходники, не билд):
- `deb/control`, `apk/APKBUILD`, `aur/PKGBUILD` - с плейсхолдерами `__VERSION__` / `__SHA256__` (sha256 tarball'а), подставляются на CI
- `winget/*.yaml` - манифесты (фаза 2)
- `visend-dispatch` - шим выбора node/bash
- `keys/` - публичные ключи (apt GPG, apk RSA), копируются на gh-pages

### CI/CD

`.github/workflows/release.yml`. Триггер - пуш тега `v*`; `workflow_dispatch` - dry-run: собираем всё, ничего не публикуем. Публикация - только на тег.

Порядок job'ов:
1. lint - синтаксис всех трёх платформ (node --check / bash -n / парсер pwsh)
2. build - tarball, .deb, .apk → `releases/<tag>/` + checksums. deb - dpkg-deb, apk - в alpine-контейнере через abuild (подпись ключом из секретов)
3. github-release - всё из `releases/<tag>/` в GitHub Release
4. npm - publish `nodejs/`
5. repos - gh-pages: apt-индексы (apt-ftparchive + GPG-подпись), apk-индексы (apk index + abuild-sign), публичные ключи. После github-release - tarball уже должен быть доступен по URL
6. aur - PKGBUILD + .SRCINFO с подставленными версией и sha256, пуш в AUR ssh-ключом. Тоже после github-release
7. docker - build & push образа сервера в ghcr

Секреты CI (генерятся один раз локально): `NPM_TOKEN`, `AUR_SSH_KEY`, `APT_GPG_KEY`, `APK_SIGN_KEY` - приватные части; публичные - в `packaging/keys/` в репо.

CI-инструменты (alpine-sdk, apt-ftparchive, pkg и т.д.) - обвязка билда, зависимостями CLI не считаются: CLI остаётся 0-dep.
